# Real Estate Aggregator

Універсальний агрегатор оголошень про нерухомість. Програма періодично
опитує сайти нерухомості, залишає лише оголошення, що відповідають вашим
критеріям, запам'ятовує вже побачені в базі SQLite і надсилає сповіщення
(в термінал та/або на email) **лише про справді нові** оголошення.

Усі критерії пошуку задаються в текстовому файлі **`config.yaml`** — код
чіпати не потрібно.

Підключені сайти — **Immoweb.be** і **Zimmo.be** (обидва — Бельгія). Обидва
читаються через структуровані дані, а не «наосліп» через розбір HTML
(пояснення нижче, у розділі
[Як влаштовані scraper'и](#як-влаштовані-scraperи-immoweb-і-zimmo)).

## Швидкий старт

Потрібен Python 3.10 або новіший.

```powershell
# 1. Перейти в теку проєкту
cd C:\Users\zetsu\Desktop\real-estate-aggregator

# 2. (рекомендовано) створити віртуальне середовище
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# 3. Встановити дві бібліотеки
pip install -r requirements.txt

# 4. Відредагувати config.yaml під себе (див. розділ нижче)

# 5. Запустити один прохід
python main.py
```

Перший запуск додасть усі знайдені оголошення в базу і покаже їх у
терміналі. Наступні запуски показуватимуть лише те, що з'явилося після
попереднього разу.

## Структура проєкту

```

│
├── config.yaml            ← ВАШ файл налаштувань. Тільки його ви й редагуєте.
├── .env.example           ← шаблон для пароля пошти (скопіювати в .env)
├── requirements.txt       ← список зовнішніх бібліотек (requests, PyYAML)
├── main.py                ← файл, який ви запускаєте
├── README.md              ← цей файл
│
├── aggregator/            ← увесь код програми, розбитий на маленькі частини
│   ├── __init__.py        ← позначає теку як Python-пакет + опис
│   ├── config.py          ← читає config.yaml і перевіряє його на помилки
│   ├── models.py          ← клас Listing: єдиний формат одного оголошення
│   ├── filters.py         ← лишає оголошення, що відповідають критеріям
│   ├── database.py        ← зберігає оголошення в SQLite, відсіює вже відомі
│   ├── notifier.py        ← сповіщення: у термінал і/або на email (smtplib)
│   ├── proximus.py        ← перевіряє, чи є за адресою оптика Proximus
│   ├── config_editor.py   ← точково змінює розділ search: у config.yaml
│   ├── runner.py          ← «диригент»: об'єднує все в один робочий цикл
│   │
│   └── scrapers/          ← по одному модулю на кожен сайт
│       ├── __init__.py    ← вмикає (реєструє) всі scraper'и
│       ├── base.py        ← BaseScraper: спільний інтерфейс + реєстр
│       ├── immoweb.py     ← scraper конкретно для Immoweb.be
│       └── zimmo.py       ← scraper конкретно для Zimmo.be
│
├── scripts/
│   └── apply_search_criteria.py  ← застосовує форму GitHub Actions до config.yaml
│
├── .github/workflows/
│   └── check.yml          ← розклад + форма "Run workflow" для нових критеріїв
│
└── tests/                 ← автоматичні тести (стандартний модуль unittest)
    ├── test_filters.py
    ├── test_database.py
    ├── test_zimmo_scraper.py
    ├── test_proximus.py
    ├── test_config_editor.py
    └── test_apply_search_criteria.py
```

### Що робить кожен файл (простими словами)

| Файл | Простими словами |
|------|------------------|
| **`config.yaml`** | Ваш «пульт керування». Тут ви пишете, що, де і за скільки шукати. Формат YAML: відступи пробілами, списки через `- `. |
| **`main.py`** | Те, що ви запускаєте командою `python main.py`. Розбирає аргументи командного рядка, вмикає журнал, завантажує налаштування і передає роботу «диригентові» (`runner.py`). |
| **`aggregator/config.py`** | Відкриває `config.yaml`, перетворює текст на зручні Python-об'єкти й перевіряє на типові помилки. Якщо у файлі щось не так — показує зрозуміле повідомлення, а не незрозумілу помилку. |
| **`aggregator/models.py`** | Описує клас `Listing` — «картку» одного оголошення з полями `price`, `bedrooms`, `locality` тощо. Кожен scraper приводить дані свого сайту до цього єдиного вигляду. |
| **`aggregator/scrapers/base.py`** | `BaseScraper` — «шаблон» будь-якого scraper'а: створює HTTP-сесію, зберігає критерії і вимагає від кожного сайту реалізувати метод `fetch()`. Тут же невеликий «реєстр», щоб `runner.py` знаходив scraper за назвою з `config.yaml`. |
| **`aggregator/scrapers/immoweb.py`** | Конкретний scraper для Immoweb.be. Будує адресу запиту з ваших критеріїв, ходить по сторінках JSON API і перетворює кожен запис на `Listing`. |
| **`aggregator/scrapers/zimmo.py`** | Конкретний scraper для Zimmo.be. Будує адресу сторінки пошуку (населений пункт + оренда/купівля + тип житла), дістає вбудований у неї список оголошень і перетворює кожен запис на `Listing`. |
| **`aggregator/filters.py`** | Клас `ListingFilter`: бере оголошення і критерії з `config.yaml`, повертає `True/False` — підходить чи ні. Якщо якогось поля в оголошенні немає (напр. ціни) — оголошення **не** відкидається. |
| **`aggregator/database.py`** | Клас `Database`: створює файл `listings.db` (SQLite, входить у Python), запам'ятовує кожне оголошення за унікальним ключем `сайт:id` і вміє сказати, які з переданих оголошень — нові. Саме це рятує від повторних сповіщень. Тут же — перевірка «а це не те саме оголошення, що вже є на іншому сайті?» (щоб не сповіщати про одну квартиру двічі, якщо рієлтор виставив її і на Immoweb, і на Zimmo). |
| **`aggregator/notifier.py`** | Формує текст повідомлення і надсилає його: `ConsoleNotifier` друкує в термінал повний список (зручно для тестів), `EmailNotifier` шле лист через `smtplib`. Лист — короткий: лише кількість і посилання на веб-дошку (сам список із фото зручніше дивитись там). Якщо дошка не увімкнена (`webpage.url` порожній) — лист теж буде повним, бо короткий без посилання марний. Посилання в листі — не просто адреса дошки, а адреса з міткою `?since=...`: дошка відкриється одразу відфільтрованою лише на оголошення саме з цього листа (докладніше — нижче). |
| **`aggregator/proximus.py`** | Для оголошень з відомою вулицею й номером будинку питає сайт Proximus, чи є там оптоволоконний інтернет (fiber), і повертає відповідь. Результат зберігається в базі й показується на веб-дошці значком «⚡ оптика». |
| **`aggregator/config_editor.py`** | Змінює в `config.yaml` лише розділ `search:` (ціну, спальні, місто тощо), не чіпаючи решту файлу — коментарі й інші налаштування лишаються як були. Використовується формою на GitHub (нижче), а в майбутньому — і Telegram-ботом. |
| **`scripts/apply_search_criteria.py`** | Читає значення з форми GitHub Actions (Run workflow), передає їх у `config_editor.py` і перевіряє, що результат — коректний YAML, перш ніж зберегти. |
| **`aggregator/runner.py`** | Головний цикл: для кожного сайту → зібрати оголошення → відфільтрувати → записати нові в базу → сповістити про нові. `run_forever()` повторює це за розкладом. |
| **`tests/`** | Перевіряють, що фільтрація і дедуплікація працюють правильно. Запуск: `python -m unittest`. |

## Як змінювати `config.yaml`

Відкрийте `config.yaml` у будь-якому текстовому редакторі. Нижче — розбір
кожного параметра.

### `sites` — які сайти опитувати

```yaml
sites:
  - immoweb
  - zimmo
```

Список назв. Кожна має відповідати scraper'у в `aggregator/scrapers/`.
Зараз доступні `immoweb` і `zimmo`. Можна лишити лише один із них, якщо
другий вам не потрібен.

### `search` — що шукати

```yaml
search:
  transaction: sale          # sale = купівля, rent = оренда
  property_types:            # house і/або apartment
    - house
    - apartment
  price_min: 200000          # євро; null = без обмеження
  price_max: 400000
  bedrooms_min: 2            # null = без обмеження
  bedrooms_max: null
  living_area_min: 80        # м²; null = без обмеження
  postal_codes:              # бельгійські індекси, у лапках
    - "9000"
    - "9040"
  localities: []             # напр. ["gent"] — лишати лише де в назві є "gent"
```

Правила:

- **`null`** означає «без обмеження». Не пишіть `0`, якщо маєте на увазі «будь-яка ціна».
- **Поштові індекси** беріть у подвійні лапки: `"9000"`, а не `9000`.
- Щоб шукати **по всій Бельгії**, залиште `postal_codes: []`.
- **`localities`** — це додатковий фільтр за підрядком у назві населеного пункту (регістр не важливий). Порожній список = не фільтрувати.
- Відступи — **пробіли** (зазвичай 2), не Tab. Це вимога формату YAML.

### Простіший спосіб змінити критерії — форма на GitHub (без редагування файлу)

Якщо проєкт уже підключено до GitHub (див. `SETUP-GITHUB.md`), критерії
пошуку можна міняти через звичайну форму — без відкриття `config.yaml`
і ризику зламати відступи:

1. У репозиторії на GitHub відкрийте вкладку **Actions**.
2. Зліва виберіть **«Перевірка нових оголошень»**.
3. Праворуч — кнопка **Run workflow**. Натисніть.
4. З'явиться форма з полями: оренда/купівля, тип житла, ціна, спальні,
   площа, поштові індекси, населені пункти.
5. Заповніть **лише те, що хочете змінити** — решту залиште порожньою
   (або «(без змін)» у випадаючих списках). Щоб прибрати обмеження
   (напр. «будь-яка ціна») — напишіть слово `null`.
6. Натисніть зелену кнопку **Run workflow** знизу форми.

Програма перевірить сайти вже з новими критеріями і сама збереже їх у
`config.yaml` — тож і всі наступні автоматичні перевірки (кожні 6 годин)
теж будуть з новими критеріями, доки ви їх знову не зміните.

Технічно за це відповідають `.github/workflows/check.yml` (сама форма)
і `scripts/apply_search_criteria.py` (застосовує її значення до
`config.yaml`, змінюючи лише потрібні рядки — решта файлу, разом з усіма
коментарями, лишається такою, як була).

### `poll` — розклad (тільки для `--loop`)

```yaml
poll:
  interval_minutes: 30
```

Як часто перевіряти сайти, коли програма запущена в режимі `python main.py --loop`.

### `database` — де зберігати

```yaml
database:
  path: listings.db
```

Ім'я файлу бази SQLite. За замовчуванням створюється в теці проєкту.
**Не видаляйте цей файл** — інакше програма «забуде» всі оголошення і
надішле сповіщення про них повторно.

### `http` — мережа

```yaml
http:
  request_delay_seconds: 1.0   # пауза між сторінками (ввічливість до сайту)
  max_pages: 10                # запобіжник: максимум сторінок за прохід
  timeout_seconds: 20
```

### `notifications` — сповіщення

```yaml
notifications:
  method: console              # console | email | both
  email:
    ...
```

- `console` — просто друкувати в терміналі (добре для перших тестів);
- `email` — надсилати лист;
- `both` — і те, і те.

Блок `email:` потрібно заповнювати, лише якщо `method` — `email` або `both`.

### `fiber_check` — перевірка оптоволоконного інтернету

```yaml
fiber_check:
  enabled: true
```

Якщо `true` — для кожного **нового** оголошення з відомою вулицею й
номером будинку програма питає сайт Proximus, чи є там оптика, і показує
результат на веб-дошці значком «⚡ оптика Proximus». Працює лише для
Бельгії. Якщо вулицю визначити не вдалося (буває приблизно у 5–7%
оголошень) — значок просто не з'являється, оголошення нікуди не зникає.

Це неофіційний механізм (детальніше — у `aggregator/proximus.py`), тож
якщо колись перестане працювати — просто вимкніть (`enabled: false`).

## Email-сповіщення

Пароль **не зберігається** в `config.yaml`. Програма читає його зі змінної
середовища, ім'я якої вказане в `password_env` (за замовчуванням
`AGGREGATOR_SMTP_PASSWORD`).

### Приклад для Gmail

1. У Google-акаунті увімкніть двофакторну автентифікацію.
2. Створіть **App Password** (пароль застосунку): Google Account →
   Security → App passwords. Отримаєте 16-символьний рядок.
3. Заповніть блок `email:` у `config.yaml`:

   ```yaml
   notifications:
     method: email
     email:
       smtp_host: smtp.gmail.com
       smtp_port: 587
       use_tls: true
       username: your.address@gmail.com
       password_env: AGGREGATOR_SMTP_PASSWORD
       from_address: your.address@gmail.com
       to_addresses:
         - your.address@gmail.com
   ```

4. Передайте пароль через змінну середовища (PowerShell):

   ```powershell
   $env:AGGREGATOR_SMTP_PASSWORD = "ваш-app-password"
   python main.py
   ```

   Щоб не вводити щоразу, можна скопіювати `.env.example` у `.env`,
   вписати пароль туди і завантажувати його перед запуском (напр. через
   пакет `python-dotenv` — його не встановлено, це на ваш розсуд).

## Посилання в листі показує лише нові оголошення

Кожен лист має свою власну адресу дошки — не просто
`https://.../real-estate-aggregator/`, а з доданим шматком `?since=...`
(час цього конкретного проходу). Дошка вміє його читати:

- відкривши дошку **з листа**, ви одразу побачите лише ті оголошення, що
  прийшли саме в цьому листі, і вгорі буде синя підказка з кнопкою
  **«Показати всю дошку →»**;
- відкривши дошку **напряму** (без `?since=`, напр. із закладки) —
  побачите звичайний повний список за 90 днів, як і раніше.

Технічно: `aggregator/runner.py` перед відправкою листа додає до адреси
дошки час поточного проходу, а `docs/index.html` порівнює його з полем
«вперше побачено» кожного оголошення.

## Як додати новий сайт

Модульність зроблена саме заради цього. Щоб підключити, наприклад,
Immoscout:

1. Створіть файл `aggregator/scrapers/immoscout.py`.
2. Опишіть клас, що успадковує `BaseScraper`:

   ```python
   from ..models import Listing
   from .base import BaseScraper, register

   @register
   class ImmoscoutScraper(BaseScraper):
       site_name = "immoscout"

       def fetch(self):
           # ... сходити на сайт, використовуючи self.criteria і self.http ...
           # ... для кожної знайденої нерухомості:
           yield Listing(site=self.site_name, site_listing_id=..., url=..., title=..., ...)
   ```

3. Додайте рядок у `aggregator/scrapers/__init__.py`:

   ```python
   from . import immoscout  # noqa: F401
   ```

4. Впишіть `immoscout` у `config.yaml -> sites`.

Фільтрація, база даних і сповіщення запрацюють автоматично — їх чіпати не треба.

## Як влаштовані scraper'и (Immoweb і Zimmo)

Обидва scraper'и уникають «наосліп» розбору HTML (коли доводиться руками
вигризати числа й текст із верстки сторінки) — але роблять це по-різному,
бо самі сайти влаштовані по-різному.

### Immoweb — прихований JSON API

Сторінка пошуку Immoweb під капотом звертається до тієї самої адреси, що
й у браузері, але якщо надіслати запит із заголовком
`Accept: application/json`, сервер повертає **структуровані дані (JSON)**,
а не HTML-розмітку:

```
https://www.immoweb.be/en/search-results/house-and-apartment/for-sale
    ?countries=BE&page=1&orderBy=newest&minPrice=200000&maxPrice=400000&postalCodes=9000
```

Відповідь містить список `results`, де кожен елемент — одне оголошення з
полями `id`, `property` (тип, спальні, площа, локація), `transaction`,
`price`. Реалізація — у `aggregator/scrapers/immoweb.py`.

### Zimmo — дані, вбудовані в сторінку

У Zimmo такого окремого API немає, зате звичайна сторінка результатів
пошуку (та сама, що у браузері) вже містить повний список оголошень як
готовий шматок JSON просто всередині HTML — у виклику
`app.start({ ... properties: [...] })`. Scraper відкриває цю сторінку і
дістає звідти саме цей шматок — структуровані поля (ціна, спальні,
площа, адреса), а не текст для читання людиною.

Адреса сторінки пошуку виглядає так:

```
https://www.zimmo.be/nl/gent-9000/te-huur/appartement/?p=2
                          │           │       │           │
                   населений пункт  оренда  тип житла   сторінка
```

Частину адреси з населеним пунктом (`gent-9000`) scraper будує сам:
один раз завантажує з відкритого довідника `geo-api.zimmo.be/places`
список усіх населених пунктів Бельгії з їхніми поштовими індексами і
знаходить потрібні. Якщо `postal_codes` у config.yaml порожній —
використовується загальна адреса пошуку по всій країні.

Реалізація — у `aggregator/scrapers/zimmo.py`.

**Обмеження Zimmo:** сайт не завжди віддає житлову площу в списку
результатів (у частини оголошень це поле порожнє). Такі оголошення не
відкидаються — просто фільтр за `living_area_min` для них не спрацьовує
(як і для будь-якого поля, якого сайт не дав).

### Одна квартира на двох сайтах — не два листи

Той самий рієлтор нерідко виставляє те саме оголошення і на Immoweb, і
на Zimmo. Щоб не надсилати про нього два окремі листи, `database.py`
перевіряє: чи немає вже в базі оголошення з іншого сайту з таким самим
типом угоди, типом житла, поштовим індексом і ціною (а якщо відома
житлова площа з обох боків — вона теж має збігатися, ±3 м²). Якщо так —
нове оголошення все одно зберігається (посилання на обидва сайти не
губляться), але сповіщення про нього не дублюється.

Це евристика (приблизне вгадування), а не 100% гарантія: теоретично дві
різні квартири в одному будинку з однаковою ціною й площею можуть
випадково «злипнутися» в одну. На практиці такий збіг рідкісний.

### Спільна ідея

- **стабільність** — верстка сайту змінюється часто, структура даних майже ніколи;
- **швидкість і чистота** — не треба «вигризати» числа з тексту;
- **менше блокувань** — акуратна кількість запитів замість десятків на кожну дрібницю.

## Застереження

- Це навчальний/портфельний проєкт. Використовуйте помірний темп запитів
  (`request_delay_seconds`) і поважайте умови використання сайтів.
- Приховані API не документовані офіційно — назви полів чи параметрів
  можуть змінитися. Тому «точна» фільтрація дублюється на боці програми
  (`filters.py`), і навіть якщо параметр у запиті застаріє, зайві
  оголошення все одно відсіються.
- Immoweb за захистом Cloudflare. Якщо запити почнуть відхилятися,
  спробуйте оновити `user_agent` у `config.yaml -> http`.
- Zimmo окремо захищає деякі свої службові адреси через Cloudflare
  (наприклад маршрутизатор JS), але сама сторінка пошуку — ні. Якщо це
  колись зміниться і scraper почне отримувати `403`, знадобиться
  окремий обхід — напишіть, розберемось разом.
